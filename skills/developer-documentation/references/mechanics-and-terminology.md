# Mechanics and terminology

Open this reference when resolving grammar, punctuation, naming, or exact word-choice questions.

## Decision order

1. Follow the project's explicit style, glossary, UI, and public API.
2. Preserve consistency with nearby documentation when it doesn't create a correctness or accessibility problem.
3. Apply the defaults in this skill.
4. For an exact term not covered here, consult the [Google developer documentation word list](https://developers.google.com/style/word-list), then a current general dictionary or another relevant technical style guide.

Record intentional project-specific exceptions in the project's own guidance rather than repeatedly rediscovering them.

## Default mechanics

- Use US English spelling and punctuation unless the project specifies otherwise.
- Use sentence case and avoid unnecessary capitals or all-caps prose.
- Use the serial comma in a series of three or more items.
- Use straight quotation marks and apostrophes in source files unless the publishing system transforms them.
- Avoid semicolons when two sentences are clearer. Avoid exclamation points in ordinary technical documentation.
- Use em dashes sparingly for interruption. Don't substitute hyphens for em dashes.
- Avoid ellipses for hesitation or omitted procedural content.
- Avoid slashes for alternatives; write _and_ or _or_. Preserve slashes in code, URLs, and paths.
- Don't use an apostrophe to form a plural. Don't pluralize or possess code identifiers and trademarks directly; add a descriptive noun or rephrase.
- Use parentheses sparingly. Move essential conditions or explanations into the sentence.
- Avoid footnotes; integrate the information, add a note, or link to a focused page.

## Names

- Match official product, feature, command, and UI names exactly.
- Don't use a product, feature, code identifier, or trademark as a verb.
- Don't shorten a name unless the short form is official, familiar to the audience, or defined.
- Treat feature names as common nouns unless the product or project explicitly capitalizes them.
- Don't depend on capitalization alone to distinguish a concept from an implementation symbol.

## Numbers and notation

- Use a hyphenated word for an ordinal when it improves readability, but prefer numerals for technical sequences, versions, steps, and measurements.
- Use "to" for prose ranges when a hyphen could be ambiguous. Preserve mathematical and code notation where exact syntax matters.
- Pair abstract numerical claims with a practical implication when it helps the reader decide or act.
- Use real mathematical notation or an accessible equation format, not improvised ASCII when the publishing system supports a clearer semantic form.

## Consistency audit

Search the document for competing forms of:

- product and feature names
- abbreviations and their expansions
- capitalization and hyphenation
- code identifiers and placeholder names
- requirement words such as _must_, _can_, _might_, and _should_
- UI labels and action verbs
- date, time, unit, and version formats
